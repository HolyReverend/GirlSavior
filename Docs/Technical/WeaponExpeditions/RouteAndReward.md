# Weapon expedition route, pickup and extraction

## Destination setup

Add `Expeditions/GirlSaviorExpeditionRoute.h/.cpp` and `Expeditions/GirlSaviorExpeditionInteractionPoint.h/.cpp` under `GirlSavior/Source/GirlSavior/`. Add an optional `EditInstanceOnly` route reference to `AGirlSaviorCombatEncounter`. Assign it on the two weapon-search maps. The route has an authored `MissionId` and three map actor references `WeaponPickup`, `EarlyExtraction` and `FinalExtraction`. Each point has a scene root, a query-only pawn overlap volume and optional presentation components. Set each point's kind to `WeaponPickup`, `EarlyExtraction` or `FinalExtraction` using `EGirlSaviorExpeditionInteractionKind`. The map actor provides shape and placement. The launch spec supplies the reward row ID.

During `InitializeRun`, require the claimed `WeaponSearch` snapshot and an assigned route to agree. Bind the actor before `CommitLaunch`. Its binding uses the following scene contract.

- Resolve the spec's room IDs against the encounter's `Rooms` array. Require one matching `AGirlSaviorCombatRoom` actor for each step, a unique ID per instance, an exact match of the room sets and reciprocal links between consecutive rooms. Take the first combat activation room from the first resolved step. Array order on the map is irrelevant to weapon searches.
- For each `DefeatPlacedEnemies` step, take its outgoing door from the room link to its immediate successor. Require the same door in both directions and `bStartsOpen == false`. Every other link is always passable or starts open. For this delivery, the only closed progression door separates room 2 from room 3. Record all declared doors for route blocking checks even when waves are disabled. Reuse the existing door collision and dynamic navigation modifier when calling `SetOpen(true)`.
- Use existing `PlacedEnemies` and each enemy's existing definition and fixture bounds. Each living enemy must register successfully in exactly one active room identified from its authored position. Refuse initial setup if required actors, definitions or fixture room bounds are missing, an enemy fails registration, or a required clear room has no enemies. Require the advertised roles and placed roles to match as sets. Place zero enemies in the reward room. Keep the existing permissive fixture behavior for legacy combat.
- Reuse the wave-free placed-enemy path with `bWavesEnabled = false`. Refactor only the room, door and registration setup needed for this mode. The encounter still owns safe-area protection, combat activation, damage, presenters and threat cleanup. Keep `CanEnemyEngage` fixture bounds and existing movement, line of sight, camera and dash checks. Do not bind or run refill profiles for these routes.
- The encounter reports a confirmed lethal event with the dying actor's registered identity before it removes the entry. Extend the enemy death call site in `Enemies/GirlSaviorEnemyCharacter.cpp` to notify the encounter before unregister. The route consumes each required actor once. Generic removal and EndPlay do not count as a kill. An unexpected required enemy removal during a live route enters the existing recovery flow so the door cannot remain permanently blocked. Disable this check during terminal cleanup and world teardown. Evaluate clearance only after a valid active run.
- Locate the three distinct points in the same world and on navigable floor. Reserve room 3 for the pickup and final point, with separation so their prompts cannot overlap. Put the early point between rooms 1 and 2. Keep Spawn and the initial safe pocket outside all extraction volumes. Disable the encounter's legacy `ExitVolume` success branch for weapon searches. The point actors never own travel, saves or terminal state.

Validate actor binding after reload and in a cooked runtime. Check gate collision and nav on both sides, a walkable backtrack path to the early point, spawn-to-entry clearance, and the pickup/final point separation. Use the existing [room design rules](../../GameDesign/Mechanics/Expeditions/AbyssRoomDesign.md) and [combat room rules](../../GameDesign/Mechanics/Expeditions/ExpeditionLevelDesign.md).

## Blockout recipe

Create two maps under `/Game/Maps/TestMaps/`. Copy shared wiring from `CombatPrototypeRoute` into each, then replace its geometry and route actors with the configuration below. Use `BP_CombatGameMode`, `BP_CombatCharacter`, the existing camera and bounds, `BP_CombatFeedbackPresenter` and current combat HUD/overlay. Keep a short entry safe pocket attached to room 1 and a connector for the early point. Count three room volumes per map. Mark each room even if its visual boundary is an arch. The settings below are initial test content.

| Map and mission ID | Room 1 and early return | Room 2 and gate | Room 3 and final return |
| --- | --- | --- | --- |
| `SupplyVault`, `WeaponSearch.Shotgun` | `Supply.Entry`, `PassThrough`. One Pursuer in the entry hall. Rope, crates and mooring rings mark the supply theme. Early return in the connector beyond the first room. | `Supply.Storage`, `DefeatPlacedEnemies`. Two Pursuers and one Shooter. Provide a loop around cover and space to dash clear of the group. Defeating these three opens the storeroom gate. | `Supply.Cache`, `RewardRoom`. Shotgun in a readable weapon crate inside the storeroom. Final return beyond the crate. |
| `AbandonedGuardroom`, `WeaponSearch.AssaultRifle` | `Guard.Entry`, `PassThrough`. One Shooter with line of sight through the checkpoint and cover available to the hero. Create `DA_Expedition_SupplyVault`, `DA_Expedition_AbandonedGuardroom` and `DA_ExpeditionCatalog` under `/Game/Data/DataAssets/Expeditions/`. Put the supply expedition first and the guardroom second. Store the exact reward row IDs `Shotgun` and `AssaultRifle`. Use `T_Expedition_SupplyVault` and `T_Expedition_AbandonedGuardroom` under `/Game/Art/Textures/Expeditions/`. Create distinct square location icons from the blockouts or authored icon art. Read the pickup mesh from `FGirlSaviorWeaponRow::Presentation.HeldMesh` and keep the point location stable regardless of the visual child. Add both maps to `[/Script/UnrealEd.ProjectPackagingSettings]` in `GirlSavior/Config/DefaultGame.ini` under `MapsToCook`. Include the same maps when passing an explicit `-map` list to UAT.

## Interaction and result

Reuse the existing Enhanced Input `IA_CampInteract` asset for physical key E. Add `/Game/Input/IMC_ExpeditionInteraction` to `BP_PlayerController` through editable defaults. Install the new context and one `Started` binding in the base controller after successful route binding. Retain the binding handle, then remove it and the context on possession change, terminal state, recovery and EndPlay. Reinstall both when a replacement hero successfully binds. The Camp subclass keeps its existing Camp-only setup. Use the focused game-input gate and suppression for modal UI.

Add `GetInteractionView(const AGirlSaviorCharacter&) const` and `TryInteract(AGirlSaviorCharacter&, FText& OutError)` to the route actor. The controller submits the currently bound pawn. Validate that the hero is the living, locally controlled, active encounter pawn, overlapping the point, within 200 cm of its anchor and with an unobstructed line to it. Reuse the same point evaluation for the HUD prompt and activation. On overlap ties choose the nearest available anchor with stable priority pickup, final, early. Refresh the view on active hero change, proximity, gate transitions, pickup or an error. Use the existing HUD tick for proximity and the late combat tick for outcome arbitration. Present «E · Подобрать {название оружия}» or «E · Вернуться с добычей» in the HUD and keep their widget hit testing off. Show «Цель не выполнена» at the early point while the bag is empty. Show «Сначала подберите оружие» at the blocked final point without an action hint. The objective text progresses from «Пройдите к боевому залу» to «Зачистите зал», «Найдите оружие» and «Вернитесь с оружием».

| Transition | Runtime effect |
| --- | --- |
| Exit entry safe area into first room | Start combat using the existing encounter activation. The room 1 enemies can be bypassed, and the player may take the early exit. |
| Last confirmed kill in room 2 | Open the gate once. Leave it open for the lifetime of the world. Show «Найдите оружие». |
| E at available weapon point | Require the gate open and the pending reward empty. Set one in-memory `PendingWeaponId` to the spec reward ID. Hide its mesh and prompt. Display «Оружие в сумке. Вернитесь в лагерь, чтобы открыть его». Keep the current slots and firearm instances. |
| E at either available exit | Set one pending extraction request with its kind. An early extraction is allowed with an empty bag. Final extraction requires the pickup. Revalidate living pawn, matching run and point when processing the request. |
| Hero dies before extraction commits | Clear the pending request and weapon, then publish defeat. Show the weapon as lost only if it was picked up. The next run spawns its pickup again. |
| Valid extraction with empty bag | Show the early-return outcome «Цель не выполнена» with no profile write. Keep the card available. |
| Valid extraction with a weapon | Commit the trusted reward, clear the pending item and freeze combat through `CloseRun(Succeeded)`. Publish the result «Оружие открыто» with the row display name. The outcome's «В лагерь» uses the existing return path. |
| Reward write fails | Clear the extraction request, retain the bag and active gameplay, and show «Не удалось сохранить находку. Попробуйте вернуться ещё раз.» Keep the exits available. A later E retries. Death can still lose the pending weapon. |

Track extraction request separately from run state and consume it once in the encounter's late tick in a frame after the input request. This permits any lethal damage in the request frame to win. Check receiver alive and current hero identity again immediately before the synchronous profile write. Publish the immutable outcome data before broadcasting the terminal state. Expose a read-only view containing extraction kind, objective completion and weapon status (`None`, `Extracted`, `Lost`). Reuse the existing terminal overlay and cause-of-defeat timing. An early return without pickup can still use the engine-level `Succeeded` terminal state, with the objective flag supplying the player-facing result. Put weapon and save errors in existing HUD messaging surfaces.

## Persist only on extraction

Expose `UGirlSaviorWeaponProfileSubsystem::TryUnlockWeapon(const UDataTable& Table, FName WeaponId, FText& OutError)`. Reuse the current row check and extract the alternating record write into a shared private function used by both confirmation and unlock. Validate the table and row, then treat an already-owned row as success without a write. For a new unlock, respect unreadable storage, newer schema and generation exhaustion. Write the existing schema with one added ID and the exact existing `ConfirmedLoadout`. After a successful write, update memory, generation and active record index. On a failed write, leave all three and the previous valid record as they were. Keep storage namespaces and slot positions. The reward adds no save fields.

Call the unlock once through `UGirlSaviorExpeditionSessionSubsystem::TryCommitExtractedWeapon(UWorld&, FGuid RunId, FName WeaponId, FText& OutError)`. The encounter calls it after the active route resolves an exit. The session checks phase, world, run ID, `WeaponSearch` mode and the exact reward ID in the retained launch. Share the same weapon profile resolution path as launch so native and test runs use the same store throughout. Call the profile only with the saved launch table. The save is the extraction commit. If Camp travel fails after it, retry from the result screen without granting the reward again. If the player restarts after the write, the weapon and prior slots load from the profile. This stage keeps an active run and its result in memory for the current game instance. The full active-run/checkpoint and result-restoration work remains in the [save design](../../GameDesign/Mechanics/Progression/SaveProgress.md).
