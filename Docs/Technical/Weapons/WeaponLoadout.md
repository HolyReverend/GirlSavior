## Profile and persistence

Use a `UGirlSaviorWeaponProfileSubsystem` on the existing `UGameInstance`. Give it `GetConfirmedLoadout()`, `GetUnlockedWeaponIds()`, `EnsureLoaded(const UDataTable&, FText&)` and `TryConfirmLoadout(const UDataTable&, const FGirlSaviorWeaponLoadout&, FText&)`. Initialize on the first table visit or a launch from Camp, after access to the table. Put persistent state in `UGirlSaviorWeaponSaveGame`, with `SchemaVersion = 1`, a monotonically increasing `Generation`, `UnlockedWeaponIds`, and the three ordered IDs of `ConfirmedLoadout`. The new profile always has `Pistol` unlocked and slot 1 equipped. Store no runtime class, icon, map instance, or actor in the file.

Use `UGameplayStatics::SaveGameToSlot` for this small explicit menu transaction. Keep two records `WeaponProfile_A` and `WeaponProfile_B` for the current single local profile (user index `0`). Load the newest readable, schema-supported record. Write the whole candidate to the other slot and update the in-memory profile only after successful write. A failed write leaves the prior slot available and the draft open with a retry message. A missing pair starts a new profile. When records exist and neither is readable, show a profile error and leave the records available for recovery. A newer unsupported schema blocks writes until migration. No autosave runs from widget redraws or travel. Use per-test temporary namespaces and release test files after checks. [Epic SaveGame documentation](https://dev.epicgames.com/documentation/en-us/unreal-engine/saving-and-loading-your-game-in-unreal-engine)

On load, ensure `Pistol` is unlocked, deduplicate ownership, normalize unknown, locked or duplicate slot IDs to empty (keep the first valid occurrence), and fall back to slot 1 `Pistol` if all are empty. Preserve the positions of other valid slots. Retain unknown ownership IDs in the persisted data to allow return of removed content or a future migration, but display only catalog entries. A missing or invalid `Pistol` row is a catalog error. When the user is editing or launching, reject invalid choices with the actual reason instead of normalizing the draft. The last valid confirmed loadout is independent of the support pair and of whether the next launch succeeds.

## Weapon page at the table

Extend `AGirlSaviorCampPlayerController`'s existing page flow and add `UGirlSaviorWeaponLoadoutWidget` in `Weapons/GirlSaviorWeaponLoadoutWidget.{h,cpp}` with `/Game/Blueprints/Camp/UI/WBP_WeaponLoadout`. The table uses its existing interaction target. Add «Набор оружия» on both the missions and preparation views in `WBP_CampPreparation`, and three read-only slot previews on preparation. Present the weapon page in the same managed Camp modal, with one input owner and explicit focus. Remember which view opened it, and keep the original mission and support draft while navigating.

```text
E at table → Missions ↔ Preparation
                 ↓           ↓
                  Weapon loadout
          Confirm or Back → opening view
```

1. On entering the page, copy the confirmed three positions into a draft owned by the Camp controller. Display cards ordered by `DisplayOrder` and ordered slots labeled `1`, `2`, `3`. A card shows icon, name, description and lock reason for unavailable weapons. The widget sends intents only and never writes profile state.
2. Select an owned card, then select a slot. If the card is outside the current draft, assigning it fills the empty slot or replaces its occupant. A card already in another slot moves to an empty destination, or swaps positions with the occupied destination. Selecting its own slot changes nothing. Each filled slot has «Убрать». An empty intermediate draft is allowed. The page offers click and keyboard focus navigation with Enter/Space activation.
3. «Подтвердить» is active only when the draft is valid and has at least one weapon. On activation the controller revalidates ownership, uniqueness, and rows, then commits via the subsystem. After success, refresh the previews for the parent panel. Both confirmation and Cancel/Esc return to the opening view and focus its «Набор оружия» action. Cancel/Esc discards changes to weapon slots. Closing the whole table discards drafts. A successful confirmation survives going back, closing the table, changing mission, and victory or defeat.
4. «Отправиться» uses the committed profile and the existing Camp rule of two distinct offered support cards. While a launch is pending, block ambiguous UI actions and repeated requests using the existing guard. A rejected launch displays a reason and re-enables the appropriate controls. The Camp controller retains UI-only modal behavior and restores the existing gameplay input/focus on exit. Bind button actions once and detach delegates when the screen is destroyed.

## Travel and run lifetime

1. Add `WeaponTable` to `UGirlSaviorCampDefinition`. Extend `UGirlSaviorExpeditionSessionSubsystem::RequestLaunch` to obtain the current confirmed profile from its owning game instance, validate it against the Camp catalog again, and resolve all occupied rows before creating a pending request. Keep the existing support resolution. The launch stores the immutable `FGirlSaviorWeaponLoadout` and three reflected `FGirlSaviorResolvedWeaponSlot` values, with empty slots represented by an empty ID. Ensure this snapshot can survive `OpenLevel` and garbage collection. The URL still contains only `CampRunId`.
2. In `AGirlSaviorCombatEncounter::InitializeRun`, use the validated snapshot for `Claimed`, existing Camp recovery for `Rejected`, and the existing early return for `Duplicate`. A `Standalone` combat map resolves `Pistol / None / None` through `DefaultWeaponTable` on `BP_CombatCharacter`, with standalone Retry intact. Demo's independent firing lane continues to use its existing simple projectile settings. The Camp pawn remains fire-disabled.
3. Before `BindHero` exposes the hero and before `CommitLaunch`, configure all weapons together and select the first occupied index for a new run, then attach support and bind the current input and presentation paths. Support's cadence validation needs the configured rows. Emit `OnHeroChanged` only after the hero has a valid set. Encounter initialization is allowed while the run is waiting. Firing requires `Active`. Clear partial setup and use trusted Camp recovery on bad data or failed initialization. A direct-start map with a bad table logs the content error and leaves firing disabled. Preserve the current return/retry routing and pending-travel recovery. [Existing Camp handoff](../CampPrototype/ExpeditionHandoff.md)
4. On a transient rebind of the same pawn in the same run, keep its instances, active slot and deadline. Cancel the current fire press. On replacement by a different valid pawn, reapply the same snapshot and most recent active slot, preserve any still-unpaid global shot deadline, and start new weapon-local spread state. Keep selection read-only outside `TrySelectWeaponSlot`. An encounter may retain the active index and deadline for rebind as transient values. At terminal state, close new fire and switch input and let existing cleanup remove projectiles. Camp return clears the run, leaving the confirmed profile untouched. The next fresh run starts in its first occupied slot.

## Access before rescue maps exist

The current Camp catalog links a generic combat route. It has no Liora supply branch or Ida rescue reward room. For this delivery, add an explicit Development and PIE playtest profile via the startup parameter `-GirlSaviorWeaponPlaytest`, with `WBP_WeaponLoadout` still using the same normal profile API. It uses `WeaponPlaytest_A/B` and begins with all three owned when that profile has no records. Its default slot order still starts with the pistol alone. It is available in a non-Shipping build started on Camp and in a fresh editor process with the argument. Automation may initialize an equivalent isolated fixture through a test-only profile backend. Direct-entry combat fixtures continue to start with a pistol. Shipping uses the normal profile. The first playable target is to equip all three at the table in that playtest profile and use each on the linked route.

When the rescue and expedition bag systems arrive, place the [shotgun](../../GameDesign/Mechanics/Weapons/Shotgun.md#получение) and [rifle](../../GameDesign/Mechanics/Weapons/AssaultRifle.md#получение) in their authored rescue branches. A pickup adds a unique weapon row ID to temporary bag data. An eligible successful extraction grants only those IDs present in the extracted bag and commits them together with the expedition result. Defeat discards temporary IDs, opening the result twice is idempotent, and a later run only spawns the weapon pickup while it remains locked. Keep the existing confirmed positions after an unlock. The player chooses whether to equip it at the table. Only the future extraction result code can grant real ownership. That integration replaces the narrow weapon save backend with the shared progression record while preserving `ConfirmedLoadout` and stable IDs.
