# Weapon system implementation plan

> For implementation agents. Follow the project's [implementation rules](../ImplementationRules.md) and the stage orchestrator. Mark each stage after recording its evidence.

**Goal** — Equip the pistol, shotgun and assault rifle at the Expedition Table, take all three onto the Camp-linked route and use them with distinct feedback.

**Status on 2026-11-24** — Technical plan. Build, editor wiring and playtest are pending.

**Read in order** — [Architecture and interfaces](WeaponArchitecture.md) → [Data and combat](WeaponDataAndCombat.md) → [Camp selection and travel](WeaponLoadout.md) → [Presentation and HUD](WeaponFeedback.md).

**Environment** — Unreal Engine 5.9 Preview, existing `GirlSavior` Runtime module, C++ gameplay, Enhanced Input, DataTable, and UMG/Blueprint content. Target the existing `CampPrototype` → `CombatPrototypeRoute` round trip. New gameplay classes and Blueprints use descriptive names without `Prototype`. Existing map names and fixture identifiers remain valid entry points.

## W1 · Catalog and pistol migration

- [ ] Read the saved `BP_CombatCharacter` FireComponent defaults and `DA_CombatPistol` in the editor. Record the baseline values, native fixture callers and Blueprint dependencies before editing. Reproduce Demo firing, the standalone combat pistol and the current Camp launch.
- [ ] Add `Weapons/GirlSaviorWeaponDefinition.*` and `Weapons/GirlSaviorFirearm.*`, including the three-position value, resolved slot contract and a centered discharge. Add `Weapons/GirlSaviorPistol.*`, row validation and `Tests/WeaponDefinitionTests.cpp`.
- [ ] Add the table asset and wire the pistol row into the existing native fire, projectile and encounter owners. Assign a pistol icon, the current/default held mesh and the existing shot sound so the row passes validation. Only this stage may use a partial catalog with the pistol row. Keep the existing Camp-origin starting pistol until W3 adds the launch snapshot. Remove the old editable `CombatPistol` property from the gameplay path after migrating its Blueprint reference and checking all callers. Remove `DA_CombatPistol` and the obsolete tuning class only after a reference audit, or retain any genuinely independent fixture use. Use the table as the migrated pistol's single authority for combat tuning.
- [ ] Migrate the `CombatPistol` property-dependent fixtures in `Tests/CampCombatEffectTests.cpp`, `Tests/PrototypeFeedbackCommands.cpp` and `Tests/PrototypeFirstFightAcceptance.cpp` in the same stage. Give native mechanics tests a validated pistol row fixture and make saved map probes read the configured weapon or its launch parameters. Keep the existing single-pistol support behavior until W2 migrates the weapon-source check.
- [ ] Build `GirlSaviorEditor` and run `GirlSavior.Weapons.Definitions` and the existing fire, damage and Camp regression suite. Inspect saved asset references after restarting the editor. Verify 4 shots/s at clean tick intervals, 10 base damage, correct hit and 14 m expiry, and working Demo, enemy projectile and standalone Retry paths.

## W2 · Shotgun, rifle and shared firing integration

- [ ] Add `Weapons/GirlSaviorShotgun.*` and `Weapons/GirlSaviorAssaultRifle.*`. Add their rows to `DT_Weapons`. Use valid temporary mesh, sound and icon references with positive presentation values until W4 supplies the final variants. Use a developer test fixture with resolved rows to exercise all behavior before the table page lands.
- [ ] Add one active-slot path to `Combat/GirlSaviorFireComponent.*`. Bind the three Boolean actions in `Core/GirlSaviorPlayerController.*`, with mapping registration and cleanup alongside `Encounters/GirlSaviorCombatEncounter.*`. Assign `IMC_ExpeditionWeapons` and actions on the combat controller content path. Stage output is a fixture that can fire and switch all three through the same component and numeric keys that Camp uses later.
- [ ] Extend `Combat/GirlSaviorTestProjectile.*` and `Combat/GirlSaviorDamageTypes.h` with the launch metadata and falloff. Update `Support/GirlSaviorSupportRun.cpp`, projectile admission and the existing Camp support probes for the typed hero weapon marker. Keep existing damage receiver callbacks and the enemy dangerous attack slot. Add regression cases in `Tests/WeaponCombatTests.cpp`, `PrototypeFireScheduleTests.cpp` where needed, and the existing `CampCombatEffectTests.cpp`.
- [ ] Run `GirlSavior.Weapons.Combat` and `Automation RunTests GirlSavior.`. In a focused combat PIE instance verify fixed fan, rifle spread reset, no cooldown bypass, safe areas and ending a run while a projectile is in flight. Use the [acceptance matrix](#acceptance-matrix) for expected results.

## W3 · Weapon page, profile and authenticated launch

- [ ] Add `Weapons/GirlSaviorWeaponProfileSubsystem.*` and `Weapons/GirlSaviorWeaponSaveGame.h`, with record validation, retryable confirmation and an isolated playtest option. Cover fresh, old, invalid and failed-write cases in `Tests/WeaponProfileTests.cpp`.
- [ ] Add `Weapons/GirlSaviorWeaponLoadoutWidget.*` and `WBP_WeaponLoadout`. Extend `Camp/GirlSaviorCampDefinition.*`, `GirlSaviorCampPlayerController.*` and `GirlSaviorCampWidgets.*` for the table reference, draft and navigation, and update `DA_CampPrototype`, `BP_CampPlayerController` and `WBP_CampPreparation` as required. Check labels and focus from real controller input.
- [ ] Extend `Expeditions/GirlSaviorExpeditionLaunch.h`, `GirlSaviorExpeditionSessionSubsystem.*` and `Encounters/GirlSaviorCombatEncounter.*` with the validated snapshot and rebind behavior. Add coverage to `CampExpeditionSessionTests.cpp` and `CampTravelRecoveryPIE.cpp`. Exercise launch failure, recovery and report return through existing entry points.
- [ ] Run `GirlSavior.Weapons.Profile` and the full suite. Prove, through table confirmation and a process restart, that slot order is durable. Launch with a deliberate gap in slot 1. Verify initial equip and switch behavior, return after victory and defeat, and that reopening the weapon editor starts from the confirmed set after discarding an unconfirmed draft.

## W4 · Presentation, HUD and playable acceptance

- [ ] Author all three meshes, icons and shot sounds. Fill `Presentation` fields. Adapt `Feedback/GirlSaviorCombatFeedbackPresenter.*`, `BP_CombatFeedbackPresenter`, `Encounters/GirlSaviorCombatHUD.*`, `GirlSaviorCombatWidgets.*` and `WBP_CombatHUD`. Add a compact slot view, one shot cue per discharge and grouped target cues. Bind and unbind when the hero changes. Inspect geometry, physical materials, ward contacts and in-flight visuals after switching.
- [ ] Cover event counts and target grouping in `Tests/WeaponFeedbackTests.cpp` and update the relevant feedback and Camp probes. Run `GirlSavior.Weapons.Feedback` and `Automation RunTests GirlSavior.`. Re-run `GirlSavior.TestCamp`, `GirlSavior.TestCampExpeditions` and the documented `GirlSavior.TestCampRecovery` variations from [Camp acceptance](../CampPrototype/Acceptance.md). Record actual counts and inspect relevant logs.
- [ ] Run the matrix below in PIE. Package Win64 Development with the current four maps. Launch `GirlSavior.exe /Game/Maps/TestMaps/CampPrototype -GirlSaviorWeaponPlaytest -windowed -ResX=1280 -ResY=720`. Equip the three in a deliberate order, fire each on the route, return to Camp and restart. Confirm that the same table worked with the normal profile, which starts with the pistol alone. Test authored references after cooking. Verify manual sound and visual feedback in a focused game viewport.
- [ ] Record the build command, test names and pass counts, package round trip, manual outcomes and pending checks. Update [current architecture](../Architecture.md), mechanics status and open items from observed behavior after implementation. Write the project report according to the [report guide](../../../Codex/WorkReports.md).
