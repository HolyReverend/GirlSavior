# Weapon data and combat

See [ownership and C++ boundaries](WeaponArchitecture.md) and the [implementation plan](ImplementationPlan.md). Units are centimeters, seconds, degrees and damage points. Authored values come from the [pistol](../../GameDesign/Mechanics/Weapons/Pistol.md), [shotgun](../../GameDesign/Mechanics/Weapons/Shotgun.md), and [rifle](../../GameDesign/Mechanics/Weapons/AssaultRifle.md) cards.

## Author `DT_Weapons`

1. Build `GirlSaviorEditor` after adding `FGirlSaviorWeaponRow` as a reflected `FTableRowBase` subclass. In the Content Browser, create **Miscellaneous → Data Table**, select the native row struct and save `/Game/Data/DataTables/Weapons/DT_Weapons`.
2. Add the rows `Pistol`, `Shotgun`, and `AssaultRifle`. Row names are the stable IDs. The `DisplayOrder` field controls card order, with a row-name tie breaker. Confirmed slot order always comes from the profile.
3. Author Russian `FText` display names, descriptions and damage causes. Give every reflected tuning field a short Russian tooltip describing its effect and units. Use `EditAnywhere, BlueprintReadOnly` for the row so presentation can read the same values.
4. Use hard asset/class references in the table for this three-weapon set. Reference the same table in the Camp mission catalog and `BP_CombatCharacter`'s fire component direct-start defaults. A Camp launch takes its resolved definitions from the Camp reference. Both references must resolve to the same asset in content validation. The hard reference chain from the included maps brings the table and dependencies into the cook.

| Column or nested field | Type and meaning |
| --- | --- |
| `DisplayName`, `Description`, `DamageCause` | `FText`. Display in Camp, HUD and the existing damage cause. Suggested descriptions include the pistol's single accurate shot, the shotgun's close fan and the rifle's sustained middle-distance fire. |
| `Icon`, `DisplayOrder` | `TObjectPtr<UTexture2D>`, `int32`. A unique identifiable icon per weapon, ordered 10, 20, 30 for the initial rows. |
| `FirearmClass`, `ProjectileClass` | `TSubclassOf<UGirlSaviorFirearm>`, `TSubclassOf<AGirlSaviorTestProjectile>`. Concrete behavior and shared projectile implementation. |
| `DamagePerProjectile`, `ShotsPerSecond`, `ProjectileRadius`, `ProjectileSpeed` | `float`. Physical damage before defenses, discharges per second, swept sphere radius and travel speed. A shotgun discharge is one shot for cadence. |
| `FullDamageDistance`, `MaxDistance` | `float`. Flat damage through the first distance, linear falloff through the second, and expiry at the second. Equal values give hard cutoff. |
| `ProjectileCount`, `PelletStepDegrees` | `int32`, `float`. Odd count gives a centered symmetric fan. The pistol and rifle each launch one projectile. |
| `TightShotCount`, `TightSpreadDegrees`, `SustainedSpreadDegrees`, `SpreadResetSeconds` | `int32`, `float`, `float`, `float`. Rifle-only behavior. Spread angles are maximum yaw deviations on either side of current aim. |
| `Presentation` | `FGirlSaviorWeaponPresentation` nested reflected struct. Store `HeldMesh`, `HeldMeshScale`, `MuzzleOffset`, `ShotSound`, `FlashScale`, `FlashSeconds`, `KickDistance`, `KickRecoverSeconds`, `TrailLength`, `TrailWidth`, `TrailFadeSeconds` and `TrailColor`. Match asset types to the presenter (`UStaticMesh`, `USoundBase`). [Presentation authoring](WeaponFeedback.md) |

| Row | Damage × projectiles | Shots/s | Full / max distance | Radius / speed | Behavior |
| --- | --- | --- | --- | --- | --- |
| `Pistol` · Пистолет | `10 × 1` | `4.0` | `1400 / 1400` | `6 / 2000` | `UGirlSaviorPistol`, zero spread |
| `Shotgun` · Дробовик | `6 × 5` | `1 / 0.70` (enter `1.4285714`) | `300 / 800` | `4 / 2000` | `UGirlSaviorShotgun`, fixed `6°` step |
| `AssaultRifle` · Автоматическая винтовка | `5.5 × 1` | `8.0` | `700 / 1200` | `4 / 2600` | `UGirlSaviorAssaultRifle`, `3` tight shots, `1° / 4°`, `0.30 s` reset |

Shotgun and rifle radius and speed are initial implementation tuning. Pistol radius and speed follow the current native defaults. In the editor compare the saved `DA_CombatPistol` and `BP_CombatCharacter` overrides before migrating. Resolve any discrepancy against pistol acceptance and the design card. Record the chosen migration numbers once in the table.

Use `FGirlSaviorWeaponRow::IsDataValid` for asset checks and the same validation logic when resolving a live loadout. Require nonempty localized fields, icon, mesh and sound, concrete classes, finite tuning, positive damage, rate, radius, speed and max range, and `0 <= FullDamageDistance <= MaxDistance`. Validate finite lifetime and effective rate, and compare radius to the actual scaled capsule before admission. Apply class-specific checks for projectile count, fan step and rifle spread, and require positive finite presentation lifetimes and scale. Limit the initial catalog to at most five projectiles per discharge and at most 90° total fan width. A bad row or reference yields a localized failure and a log with the table, row and failing field. [Epic row validation API](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/FTableRowBase)

## Discharge and switching

1. Preserve `InputKey` fire down/up ordering and `FGirlSaviorFireSchedule`. `FireComponent` ticks after aim in `TG_PostUpdateWork`. Declare the expedition firing path on `BP_CombatCharacter` independently of whether its table reference or encounter binding is valid. A missing table or encounter leaves that path disabled. The Demo keeps its existing simple fixture path. Recheck active encounter, pawn, input/focus, constrained cursor, and fire permission before consuming a ready press. Launch at most once per tick using the current aim. A ready short tap survives release. A tap spent entirely in cooldown does not queue. Pause uses world game time. Dash and ordinary movement keep the series.
2. In `Content/Input/Actions`, create three Boolean Enhanced Input actions `IA_WeaponSlot1` through `IA_WeaponSlot3`. Map top-row `1` through `3` in `Content/Input/IMC_ExpeditionWeapons` and assign the actions and context on the existing `BP_PlayerController` used in combat. Bind `Started` in the native controller. Add the context only after the encounter binds a configured combat hero. Remove it on unbind, possession change, terminal state or teardown. Set the mapping options to ignore keys already pressed when adding the context. Require a living bound hero, a run that is `Waiting` or `Active`, playable input and an unpaused world. A bound living hero may select in the safe pocket while firing is blocked. [Epic Enhanced Input overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/input-overview-in-unreal-engine)
3. A same-slot, empty-slot or out-of-range request is a no-op. On a valid change, cancel the held and latched press, preserve the existing global deadline, update the active index and broadcast once. A fresh LMB press is required. Multiple valid key edges in one frame are processed in the order delivered, with the last accepted selection active. A stored shot due that frame is canceled by a successful switch before the post-aim tick. Cooldown swapping cannot produce extra shots.
4. Build projectile directions on the XY plane around world up. The pistol uses one center direction. The shotgun uses `((Index - (Count - 1) / 2) * PelletStepDegrees)`, yielding `-12°, -6°, 0°, 6°, 12°`. The rifle uses a single uniform yaw sample in the current angle bounds from a per-instance `FRandomStream`. Seed it at configuration, with a fixed injectable test seed. Count only actual discharges. Shots 1–3 after a reset are tight. Shot 4 and later use sustained spread. An elapsed `>= 0.30 s` since that rifle's last committed shot starts shot 1 again. A short switch or LMB release keeps the previous rifle series until the same game-time interval elapses. Preserve the stream across a rejected attempt by generating against a temporary copy and committing it with the shot.
5. Use the hero capsule center as the authoritative origin and pass each normalized direction to `SpawnCombatProjectile`. Allocate one `ShotGroupId` from the encounter per discharge and one distinct `AttackId` per projectile (the sole projectile may reuse the group ID). `AttackId` still identifies a single delivery, while the group identifies the trigger pull. Populate `FGirlSaviorDamageSpec` with `DirectProjectile`, `Hero` faction, `SourceId` of `Hero.<RowName>`, row `DamageCause`, origin and instigator. Add optional `WeaponId` and `ShotGroupId` to the typed spec, defaulted empty/zero for unrelated sources. Retain enemy attack slot ownership and distinct enemy channels.
6. Any accepted projectile, including an immediate cover stop, consumes the discharge. If one spawn fails after another succeeds, keep the successful projectiles, log the count, and consume one interval and one cue. If none succeeds, cancel the series and emit no shot feedback. Snapshot the effective rate at discharge, call `Schedule.Launched(Now, Rate)` once, advance rifle state and broadcast one `OnWeaponShot`. A support rate change applies to the next committed interval and cannot move an existing deadline. The chosen confirmation policy preserves the design's one next-shot deadline during switching. [Character shooting rules](../../GameDesign/Mechanics/Weapons/CharacterShootSystem.md#управление-и-темп)

## Contact, distance and support

Copy range, damage and trail parameters into `FGirlSaviorProjectileLaunch` before `FinishSpawning`. Add a default-disabled distance falloff option to protect existing enemy and Demo launches. At contact use the projectile center's distance traveled from its own launch origin, clamped to the sweep range. Apply `BaseDamage` through full distance. If `Full < Max`, multiply by `Clamp((Max - Distance)/(Max - Full), 0, 1)` beyond full distance. At a zero-damage contact stop the projectile, keep the terminal trail, and skip damage resolution and target hit confirmation. At hard cutoff, resolve a real swept hit reached at the range limit with full damage. Range expiry without a hit emits no impact. For example, a shotgun pellet at `550 cm` deals `3` before defenses and a rifle projectile at `950 cm` deals `2.75`.

Keep the existing initial overlap and sweep checks, capsule collision responses, safe-area clipping, door blocking and completion guard. Each of the five pellets can apply damage once, including multiple pellets to one living target. Use the receiver's existing result for barrier, health, protection and death. Send support only from the existing committed projectile-hit path. Generalize Liora's current `Hero.Pistol` check to projectile spec with a valid weapon marker, a hero source and a positive applied nonlethal result on a living registered enemy. Refresh the existing slow per victim without stacking. Ida multiplies each weapon row's rate, and Saira's barrier remains in the current receiver path. Fixture launches in native/PIE support checks should set the marker so they exercise the same rule. [Current support implementation contract](../CampPrototype/SupportSkills.md)

Use `BP_CombatPistolProjectile` as the baseline hero projectile asset. If it has pistol-specific cosmetics, create `/Game/Blueprints/Combat/BP_HeroWeaponProjectile` from the same native class, migrate the neutral visual and reference it from all hero rows. Blueprints can style the collision-free mesh. The native snapshot controls travel, damage and trail.
